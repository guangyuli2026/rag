# 步骤 4：可追溯的离线向量检索

本步完成的是可替换接口、索引生命周期和余弦排序的工程基线。
尚未选择真实 Embedding 服务商，因此没有真实语义检索效果、API 延迟或费用结果。
本步不包含混合检索、重排、生成答案或自动拒答。

## 从一个请求跟踪数据

先在项目根目录执行：

```powershell
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
.\.venv\Scripts\rag-demo.exe vector-index
.\.venv\Scripts\rag-demo.exe vector-search "RAG-101" -k 3
.\.venv\Scripts\rag-demo.exe compare -k 3
.\.venv\Scripts\python.exe -m pytest
```

1. `load_documents()` 读取资料，得到 `list[Document]`。
2. `build_vector_index()` 按相对路径去重，用同一切分配置得到 `list[Chunk]`。
3. `provider.embed_documents()` 接收片段字符串列表，返回 `N × D` 的 NumPy 矩阵。
   第 i 行必须对应第 i 个片段，N 是片段数，D 是维度。
4. `VectorIndex.save()` 将矩阵、片段列表和版本元数据保存为 `data/index/index.npz`。
5. 查询时先读取当前资料并校验索引版本；`embed_query()` 返回 `1 × D` 的查询矩阵。
6. `VectorIndex.search()` 计算每个片段与查询的余弦相似度，排序并取前 k 个。
7. CLI 展示 `chunk.relative_path`、`char_start`、`char_end` 和文本。
   在当前文档中，`doc.content[char_start:char_end] == chunk.text`。

`doc_001` 等序号在文件增删后可能变化，不能当作跨版本永久 ID。
这里通过资料版本、相对路径和原文区间追溯证据；发现资料变化就拒绝旧索引。

## 参数在哪改

| 参数 | 位置 | 当前是否有效 |
| --- | --- | --- |
| `RAG_EMBEDDING_PROVIDER=offline` | 本地 `.env` | 是，选择离线替身 |
| `RAG_OFFLINE_DIMENSION=128` | 本地 `.env` | 是，替身向量维度 |
| `RAG_OFFLINE_NGRAM_MIN=2` / `MAX=3` | 本地 `.env` | 是，连续字符特征长度范围 |
| `chunk_size=500` / `overlap=50` | `src/rag_assistant/config.py` | 是，基础块和向前扩展长度 |
| `-k 3` | 查询命令参数 | 是，最多返回 3 个片段，无需重建 |
| `RAG_EMBEDDING_MODEL` / `API_KEY` / `BASE_URL` | 本地 `.env` | 预留，适配器尚未实现 |

上述模型、输入配置和切分参数改变后均需重建索引；模型名相同、维度相同也不保证兼容。
环境变量覆盖 `.env`，因此终端中设置过同名变量时需注意优先级。
密钥不进入源码、索引元数据或日志，`.env` 被 Git 忽略。

真实服务商适配器需要依据官方文档确认：模型/修订版本、输出维度、API 地址、认证方式、
批量/长度限制，以及查询和文档是否需要不同的前缀或 task 参数。
实现 `EmbeddingProvider` 的 `embed_documents`、`embed_query` 和不含密钥的配置指纹，
再在工厂函数注册。修改 `.env` 中的模型名称本身不会安装或实现服务商接口。

## 如何判断计算正确

余弦相似度 = 点积 /（文档向量长度 × 查询向量长度）。
例如文档 `[3, 4]`、查询 `[3, 0]`，点积为 9，长度为 5 和 3，余弦为 `0.6`。
这个值说明向量方向关系，不是“答案有 60% 概率正确”。

正常非零向量的余弦范围是 [-1, 1]；零向量没有定义良好的方向，本实现排除它。
有负分并不说明计算错误。离线替身使用非负计数，所以其结果通常在 [0, 1]。
Top-k 只负责排序，不保证有答案；没有资料支持的问题也可能返回 k 条。

测试用手工指定的向量核对余弦值、排序和零向量处理，再用替身验证持久化和来源。
不通过不断降低分数阈值或针对某一道题调整替身来宣称测试正确。

## 索引更新与耗时

小数据集使用全量快照：每次 `vector-index` 重新读取当前资料并整体替换索引。
重复导入同一路径和相同内容不会产生重复；同一路径传入冲突版本会报错。
修改或删除文件后，查询会提示重建；重建后旧内容和删除的文档不再参与检索。
不同路径下的相同文本仍是不同来源，不做跨文件内容合并。

向量及 JSON 映射放在一个 `.npz` 文件内，以临时文件写完后替换。
测试覆盖中途写入失败时旧索引仍可读取；这不等于数据库级并发或断电保障。
加载时校验格式版本、模型、输入配置、维度、切分版本、资料版本、矩阵和来源映射。

构建耗时包括去重、切分、Embedding 和元数据；CLI 另报含读取和保存的总耗时。
查询耗时包括查询 Embedding、余弦计算及 Top-k；CLI 另报含索引读取和校验的总耗时。
对比报告分别累计关键词检索和向量检索时间，不把打印、关键词耗时算成向量耗时。

## 10 题草稿对比与局限

问题文件包含同义表达、跨语言、精确术语、真实存在于虚构资料中的编号、数字和无答案题。
9 题有证据，1 题无答案。原文引句必须在来源文件中唯一出现，程序据此生成字符范围。
全部标签仍标为 `pending_human_review`，需要你核对问题和证据之间的关系。

草稿证据命中率 = Top-k 中至少一个片段完整包含标注证据的题数 / 有答案题数。
同一来源中返回了错误片段不算命中；无答案题不进入这个分母。
默认配置、Top-3 的本机运行结果为：关键词 5/9，离线替身 5/9；无答案题返回空为 1/1 和 0/1。
逐题的原文位置、分数、耗时、资料版本和配置指纹记录在 `reports/retrieval-comparison.json`。
此前开发过程中的 8/9 只检查来源文档名，不是这个片段级指标，也不能与新结果直接比较。

实际案例：

- “登山杖”：关键词能命中正确证据；替身可能命中同一文档的其他片段，仍是失败。
- “办公室绿植补充水分时要注意什么？”：关键词把连续中文问题当作长关键词，因而不命中；
  替身这次能召回证据，但共享字符或哈希碰撞就可能导致这种结果，不能证明理解了同义词。
- “校园附近有地铁线路吗？”：资料中没有答案，替身仍返回片段，说明 Top-k 不是拒答逻辑。

关键词一般适合精确词语和编号；真实语义模型可能改善同义表达和跨语言问题，必须实际验证。
当前关键词基线不是 BM25，离线哈希不是语义模型，这些分数不能用于判断两类成熟方案优劣。
哈希只有 128 个桶，碰撞和文本长度会明显影响排序；不继续为这 10 道题调替身参数。
